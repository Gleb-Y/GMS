# GMS — Система управления спортивным клубом

## 1. Основной функционал приложения

**GMS (Gym Management System)** — полнофункциональное backend-приложение для управления спортивным клубом.

### Что делает приложение
GMS автоматизирует управление всеми аспектами работы спортивного клуба:
- Управление абонементами (тарифами и подписками)
- Аренда спортивных шкафчиков
- Расписание тренировок и запись на занятия
- Система уведомлений для членов клуба
- Аутентификация и авторизация пользователей
- Администраторский функционал для управления бизнесом

### Целевая аудитория
- **Владельцы спортивных клубов** — управление членской базой и доходами
- **Администраторы клуба** — контроль ресурсов и расписания
- **Члены клуба** — оплата, бронирование, управление своими данными

### Основные функции

| Функция | Описание |
|---------|---------|
| **Управление абонементами** | Активация подписок, заморозка, отмена |
| **Аренда шкафчиков** | Бронирование, управление доступом |
| **Тренировки** | Расписание занятий, запись на тренировки, управление местами |
| **Тренеры** | Регистрация тренеров, привязка к занятиям |
| **Авторизация** | JWT-токены, ролевое управление доступом (User, Admin, Coach) |
| **Уведомления** | Email-уведомления о событиях, истечении подписок |
| **Admin-панель** | Статистика, управление пользователями, доход, отчёты |

## 2. Архитектура приложения

### Общая структура

```
GMS Backend (Spring Boot 3.5.6)
│
├── Controller Layer (REST API)
│   ├── UserController — управление пользователями
│   ├── MembershipController — абонементы и подписки
│   ├── LockerController — аренда шкафчиков
│   ├── TrainingController — тренировки и бронирования
│   ├── AdminController — администраторские функции
│   └── PageController — web-интерфейс (Thymeleaf)
│
├── Service Layer (Бизнес-логика)
│   ├── UserService — управление пользователями
│   ├── MembershipService — логика абонементов
│   ├── LockerService — управление шкафчиками
│   ├── TrainingService — обработка тренировок
│   ├── AdminService — аналитика и статистика
│   ├── JWTService — генерация и валидация токенов
│   ├── EmailService — отправка писем
│   └── CustomUserDetailsService — интеграция с Spring Security
│
├── Repository Layer (Доступ к данным)
│   ├── UserRepository
│   ├── MembershipRepository
│   ├── LockerRepository / LockerRentRepository
│   ├── TrainingScheduleRepository / TrainingBookingRepository
│   ├── CoachRepository
│   └── NotificationRepository
│
└── Data Layer
    └── PostgreSQL Database
```

### Взаимодействие слоёв

```
HTTP Request
    ↓
Controller (обработка входящих запросов)
    ↓
Service (валидация, бизнес-логика)
    ↓
Repository (запросы к БД)
    ↓
PostgreSQL (хранилище данных)
    ↓
HTTP Response
```

### Основные модели данных

| Модель | Описание |
|--------|---------|
| `User` | Пользователь (email, пароль, роль, профиль) |
| `Membership` | Тариф абонемента (название, цена, продолжительность) |
| `UserMembership` | Подписка пользователя (активна ли, даты начала/конца) |
| `Locker` | Шкафчик (номер, статус, тип замка) |
| `LockerRent` | Аренда шкафчика (пользователь, период, стоимость) |
| `TrainingSchedule` | Расписание тренировки (время, место, тренер, capacity) |
| `TrainingBooking` | Запись на тренировку (пользователь, статус) |
| `Coach` | Тренер (ФИО, специализация, расписание) |
| `Notification` | Уведомление (тип, текст, статус отправки) |

### Технологический стек

| Компонент | Технология | Назначение |

### Основные компоненты архитектуры

#### Аутентификация и авторизация
- **JWT токены**: Генерируются при входе, содержат информацию о пользователе и его ролях
- **Spring Security**: Защита эндпоинтов на основе ролей (USER, ADMIN, COACH)
- **CustomUserDetailsService**: Загрузка данных пользователя из БД

#### Кеширование (Redis)
- Кеширование часто запрашиваемых данных (профили пользователей, расписание)
- Хранение сессий пользователей
- Ускорение ответов API

#### Очереди сообщений (RabbitMQ)
- Асинхронная обработка email-уведомлений
- Deferred обработка тяжёлых операций
- Гарантированная доставка сообщений

#### Email-сервис
- Отправка писем о регистрации, восстановлении пароля
- Напоминания об окончании абонемента
- Уведомления о новых бронированиях

## 3. Запуск через Docker Compose

### Сервисы, запускаемые в docker-compose

| Сервис | Образ | Порт | Назначение |
|--------|-------|------|-----------|
| `postgres` | postgres:17.0-alpine | 5432 | База данных |
| `redis` | redis:7.2-alpine | 6379 | Кеш и сессии |
| `rabbitmq` | rabbitmq:3.13-management-alpine | 5672 (AMQP), 15672 (UI) | Message broker |
| `gms-app` | Spring Boot приложение | 8080 | Основное приложение |

### Переменные окружения

Для работы приложения необходимо установить переменные окружения (создайте `.env` в корне проекта):

```bash
# Email-сервис (для уведомлений)
MAIL_USERNAME=your-email@gmail.com
MAIL_PASSWORD=your-app-password

# БД (уже настроено в compose)
SPRING_DATASOURCE_URL=jdbc:postgresql://postgres:5432/gms_db
SPRING_DATASOURCE_USERNAME=postgres
SPRING_DATASOURCE_PASSWORD=postgres

# RabbitMQ
SPRING_RABBITMQ_HOST=rabbitmq
SPRING_RABBITMQ_PORT=5672
SPRING_RABBITMQ_USERNAME=guest
SPRING_RABBITMQ_PASSWORD=guest
```

### Инструкция по запуску

#### Требования
- Docker и Docker Compose установлены
- В корне проекта (где расположен docker-compose.yml)

#### Шаг 1: Сборка и запуск контейнеров

```bash
# Запустить все сервисы в фоне
docker-compose up -d

# Или запустить с выводом логов в консоль
docker-compose up
```

Команда выполнит:
1. Скачивание образов (PostgreSQL, Redis, RabbitMQ)
2. Запуск контейнеров в порядке зависимостей
3. Сборка и запуск Spring Boot приложения

#### Шаг 2: Проверка статуса контейнеров

```bash
docker-compose ps
```

Ожидаемый вывод: все сервисы со статусом `Up`

#### Шаг 3: Проверка готовности приложения

```bash
# Дождитесь, пока в логах появится сообщение о запуске Spring Boot
docker-compose logs gms-app | tail -20

# Проверьте доступность API
curl http://localhost:8080/swagger-ui/index.html
```

#### Шаг 4: Просмотр логов

```bash
# Логи всех сервисов
docker-compose logs -f

# Логи конкретного сервиса
docker-compose logs -f gms-app
docker-compose logs -f postgres
docker-compose logs -f rabbitmq
```

#### Остановка сервисов

```bash
# Остановить контейнеры (сохраняют данные)
docker-compose stop

# Остановить и удалить контейнеры
docker-compose down

# Остановить и удалить контейнеры + томы (ОСТОРОЖНО: удалит данные БД)
docker-compose down -v
```

### Миграции БД

Flyway автоматически запускает миграции при старте приложения:

```bash
# SQL-скрипты расположены здесь:
gms/src/main/resources/db/migration/

# Миграции:
V1__Create_user_table.sql                    # Таблица пользователей
V2__Insert_test_users__ignored.sql           # Тестовые пользователи (игнорируется)
V3__Create_membership_tables.sql             # Таблицы абонементов
V4__Create_locker_tables.sql                 # Таблицы шкафчиков
V5__Create_coach_and_training_tables.sql     # Тренеры и тренировки
V6__Create_notifications_table.sql           # Уведомления
```

Миграции выполняются **автоматически** при запуске приложения в следующем порядке (по номерам версий).

#### Перестроение БД (удалить и пересоздать)

```bash
# 1. Остановить и удалить контейнеры + томы
docker-compose down -v

# 2. Заново запустить (миграции выполнятся автоматически)
docker-compose up -d
```

### Основные группы эндпоинтов

#### **Auth** — Аутентификация
- `POST /api/users` — Создать нового пользователя (регистрация)
- `POST /api/users/login` — Вход в систему (получить токен)
- `GET /api/users/{email}` — Получить профиль пользователя по email
- `PUT /api/users` — Обновить профиль пользователя
- `DELETE /api/users/{id}` — Удалить аккаунт

#### **Membership** — Управление абонементами
- `GET /api/memberships` — Список всех тарифов
- `GET /api/memberships/active` — Получить активные тарифы
- `GET /api/memberships/{id}` — Детали тарифа
- `POST /api/memberships` — Создать новый тариф (только для Admin)
- `PUT /api/memberships/{id}` — Обновить тариф (только для Admin)
- `DELETE /api/memberships/{id}` — Удалить тариф (только для Admin)
- `POST /api/memberships/purchase/{membershipId}` — Купить абонемент
- `POST /api/memberships/renew/{membershipId}` — Продлить абонемент
- `POST /api/memberships/freeze` — Заморозить абонемент

#### **UserMembership** — Управление подписками пользователей
- `GET /api/user-memberships/user/{userId}` — Получить все абонементы пользователя
- `GET /api/user-memberships/user/{userId}/active` — Получить активный абонемент пользователя
- `GET /api/user-memberships/{id}` — Получить абонемент по ID
- `POST /api/user-memberships` — Назначить абонемент пользователю (только для Admin)
- `PUT /api/user-memberships/{id}` — Обновить абонемент пользователя (только для Admin)
- `PATCH /api/user-memberships/{id}/cancel` — Отменить абонемент (только для Admin)
- `DELETE /api/user-memberships/{id}` — Удалить абонемент (только для Admin)
- `GET /api/user-memberships/expired` — Получить истекшие абонементы (только для Admin)

#### **Locker** — Управление шкафчиками
- `GET /api/lockers/available` — Список доступных шкафчиков
- `GET /api/lockers/available/count` — Количество доступных шкафчиков
- `POST /api/lockers/rent/{lockerId}` — Забронировать шкафчик
- `POST /api/lockers/release/{rentId}` — Освободить шкафчик
- `GET /api/lockers/my-rent` — Моя активная аренда шкафчика
- `GET /api/lockers/my-history` — История моих арендованных шкафчиков

#### **Training** — Управление тренировками
- `GET /api/trainings/coaches` — Получить всех активных тренеров
- `GET /api/trainings/coaches/specialization/{specialization}` — Получить тренеров по специализации
- `POST /api/trainings/coaches/create` — Создать профиль тренера (только для Admin)
- `GET /api/trainings/schedules/coach/{coachId}` — Получить расписание тренера
- `GET /api/trainings/schedules/upcoming` — Получить предстоящие тренировки
- `POST /api/trainings/schedules/create` — Создать расписание тренировки (только для Coach)
- `PUT /api/trainings/schedules/{scheduleId}` — Обновить расписание (только для Coach)
- `DELETE /api/trainings/schedules/{scheduleId}` — Удалить расписание (только для Coach)
- `POST /api/trainings/bookings/book/{scheduleId}` — Забронировать место на тренировку
- `POST /api/trainings/bookings/cancel/{bookingId}` — Отменить бронь на тренировку
- `GET /api/trainings/bookings/my-bookings` — Получить мои активные бронирования
- `GET /api/trainings/bookings/schedule/{scheduleId}` — Получить бронирования для расписания (только для Coach)
- `GET /api/trainings/schedules/{scheduleId}/available-spots` — Получить количество свободных мест

#### **Admin** — Администраторские функции
- `DELETE /api/admin/users/{userId}` — Удалить клиента
- `GET /api/admin/reports/attendance` — Получить отчёт посещаемости
- `GET /api/admin/reports/program-popularity` — Получить популярность программ тренировок
- `GET /api/admin/reports/monthly-revenue` — Получить месячную выручку
- `GET /api/admin/reports/user-statistics` — Получить статистику пользователей
- `GET /api/admin/reports/top-coaches` — Получить топ тренеров
- `GET /api/admin/users/{userId}/membership-info` — Получить информацию о членстве пользователя
- `GET /api/admin/dashboard` — Получить Dashboard с основными метриками

### Коды ответов API

| Код | Описание |
|-----|---------|
| `200 OK` | Успешный запрос |
| `201 Created` | Ресурс успешно создан |
| `204 No Content` | Успешно, но нет содержимого |
| `400 Bad Request` | Ошибка валидации данных |
| `401 Unauthorized` | Требуется аутентификация (забыли токен) |
| `403 Forbidden` | Недостаточно прав доступа |
| `404 Not Found` | Ресурс не найден |
| `409 Conflict` | Конфликт данных (например, пользователь уже существует) |
| `500 Internal Server Error` | Ошибка сервера |

## Теоретические вопросы по архитектуре и масштабированию

### 1. Как выбор структуры базы данных влияет на дизайн CRUD API?

**SQL (реляционные БД)**
- Чёткие связи, API часто имеет вложенную структуру (`/users/{id}/orders`)
- Требует продуманной схемы и транзакций, CRUD-операции строго типизированы
- Фильтрация и сортировка через сложные запросы (WHERE, JOIN)
- Строгая валидация данных на уровне БД

**NoSQL (документные, key-value)**
- Гибкая структура, API может быть менее строгим (документы с разными полями)
- Масштабирование проще, но транзакции ограничены
- Простые запросы, но слабые возможности JOIN

### 2. Какие проблемы могут возникнуть при массовых обновлениях данных через API?

- **Производительность**: сервер может быть перегружен множеством запросов
- **Консистентность**: при сбоях часть данных обновится, часть — нет
- **Блокировки и коллизии**: конкурирующие обновления могут перезаписывать изменения
- **Ограничения API Gateway**: таймауты, превышение лимитов
- **Сложность отката**: трудно восстановить прежнее состояние данных

### 3. Почему важно использовать правильные HTTP-методы?

- `GET` — только чтение, не меняет состояние (идемпотентность)
- `POST` — создание ресурса или выполнение действия
- `PUT/PATCH` — обновление ресурса
- `DELETE` — удаление

Если использовать только POST, теряются:
- Прозрачность логов и маршрутизации
- Совместимость с REST, ухудшается интеграция
- Безопасность, сложнее разделять права доступа

### 4. Какие уязвимости могут возникнуть при хранении JWT на клиентской стороне?

- **localStorage/sessionStorage**: доступны из JavaScript → уязвимы для XSS
- **Cookies без флагов HttpOnly/Secure**: могут быть украдены через XSS или перехвачены по незащищённому соединению
- **Длительный JWT**: если токен живёт долго, его могут повторно использовать
- **Утечка в логах или URL**: токен может случайно попать в логи

### 5. Когда стоит ограничивать время жизни JWT и какие проблемы это создаёт для UX?

**Зачем ограничивать:**
- Снижает риск утечки токена
- Проще отзывать доступ — токен «протухает» сам

**Минусы для UX:**
- Пользователю приходится чаще логиниться
- Нужно реализовать refresh tokens и автообновление
- Может прерывать длительные операции
- Усложняет клиентскую логику

### 6. Как логирование помогает в расследовании инцидентов безопасности?

- Фиксирует события: кто сделал запрос, когда, с какого IP и каким токеном
- Позволяет отследить цепочку атак (SQL-инъекции, подбор пароля, несанкционированные изменения)
- Помогает отследить ущерб и восстановить данные
- Позволяет выявить подозрительные паттерны (частые запросы, необычные действия)
- Помогает понять причину инцидента и предотвратить повтор

### 7. Разница между горизонтальным и вертикальным масштабированием

**Вертикальное масштабирование:**
- Увеличение мощности существующих серверов (CPU, RAM, диск)
- Централизованный кеш, проще управлять консистентностью
- Ограничено физическими пределами одного сервера

**Горизонтальное масштабирование:**
- Добавление новых серверов
- Требует распределённого кеша (Redis Cluster, Memcached)
- Лучшая отказоустойчивость

### 8. Какой риск несут фоновые задачи при сбое очереди сообщений?

- **Потеря данных**: сообщения могут исчезнуть без восстановления
- **Неконсистентность состояния**: часть задач выполнена, часть — нет
- **Накопление очереди**: после восстановления возникает лавинообразная нагрузка
- **Таймауты и дедлайны**: задачи «зависают», ожидая ресурсы

### 9. Почему важна идемпотентность задач при их повторном выполнении?

- Предотвращает дублирование: одинаковые операции не создают копии
- Повышает надёжность повторных попыток (retry)
- Обеспечивает консистентность данных при параллельном выполнении
- Упрощает откат — понятно, что именно было изменено

### 10. Что сложнее поддерживать в большой системе: код или документацию?

**Документацию сложнее, потому что:**
- Обновляется вручную и часто отстаёт от кода
- Нет автоматических тестов для проверки актуальности
- Требует коллективных усилий
- Часто считается «второстепенной» задачей
- Быстро устаревает при активной разработке

### 11. Плюсы и минусы ручного README и автогенерации

**Ручной README:**
- Понятный формат, можно объяснить «почему», а не только «что»
- Быстро устаревает
- Требует дисциплины разработчиков

**Автогенерация документации:**
- Всегда актуальна
- Полное покрытие API
- Единый стандарт оформления
- Не хватает контекста и примеров

### 12. Как документация помогает при онбординге новых разработчиков?

- Ускоряет адаптацию: понимание архитектуры, примеры, шаблоны кода
- Снижает нагрузку на команду: меньше вопросов к опытным разработчикам
- Стандартизирует процессы: чёткие руководства по разработке
